这个问题可以拆成两层：**先把"千万设备、亿级记录、毫秒查询"翻译成可量化的指标，再用数据布局、索引和预计算让查询成本只和结果大小相关，而与数据总量无关**。下面按这个思路展开。

## 一、先把需求翻译成数字

假设一个典型 IoT 负载：1000 万设备，每台 10 个测点，每 10 秒上报一次。

| 项目 | 估算 | 说明 |
|---|---|---|
| 写入行数 | 100 万行/秒，1000 万值/秒 | 每行 = 一台设备一次上报的 10 个测点 |
| 每天行数 | 约 864 亿行 | "亿级记录"实际上是一小时的量 |
| 序列数 | 1000 万（宽表模型）或 1 亿（单值模型） | 模型选择直接决定索引规模 |
| 压缩后存储 | 约 16 B/行 → 1.4 TB/天 | 时间戳 + 10 个值，按 1.5 B/值估算 |
| 30 天保留 | 约 40 TB | 需要集群 + 冷热分层 |

两个结论：

1. **亿级记录不是难点**，难点是千万级基数（cardinality）下的索引，以及持续高压写入时查询延迟不抖动。
2. **"毫秒级"必须限定查询类型**。单设备区间查询、最新值、按区域的预聚合查询可以做到毫秒；对全量原始数据做任意 ad-hoc 聚合，物理上做不到（1 亿行 × 8 B = 800 MB，单机内存带宽扫一遍也要几十毫秒以上，而且不止一列）。

| 存储管理 | TTL 自动过期；冷热分层；对象存储支持；压缩算法可选 |
| 可靠性 | 持久化语义（fsync 策略）、崩溃恢复时间、副本数、RPO/RTO |

| 查询抖动 | 写入满载时查询 p99 不超过空载 2× | 最容易被忽略的指标 |

## 三、毫秒级查询的三条核心原则

```
路由：根据设备 ID 直接定位到分片，不扫无关设备
布局：同一设备的数据在磁盘上物理连续，一次顺序读取拿到全部
预计算：跨设备聚合提前算好，查询只读聚合结果
```

只要这三条做到，查询成本就是 O(结果大小) 而不是 O(数据总量)，千万设备和百万设备没有本质区别。

## 四、整体架构

```
设备 ──MQTT/gRPC──► 接入层（协议解析、批量、限流）
                          │
                          ▼  hash(device_id) → shard
              ┌─────────────────────────────┐
              │  Shard（单线程持有，shared-nothing）│
              │  WAL ──► MemTable ──► 列式文件     │
              │  Last-Value Cache                 │
              │  Series Index + 倒排索引           │
              │  流式预聚合（1m/1h rollup）         │
              └─────────────────────────────┘
                          │
             热：内存 ─ 温：本地 NVMe ─ 冷：对象存储
                          │
元数据服务（Raft）：分片→节点映射、schema、分区目录
查询引擎：路由 → 并行扫描 → 向量化执行（Arrow）→ 合并
```

## 五、关键设计决策

### 1. 数据模型：按设备宽表，而不是每个测点一条序列

同一设备同一时刻上报的 10 个测点共用一个时间戳列。好处：

- 序列数从 1 亿降到 1000 万，索引缩小 10 倍
- 时间戳列只压缩一次，存储省 20%～30%
- 单设备查询一次读出所有字段，不需要 join

标签分两类处理：**`device_id` 不进倒排索引**，直接 `series_id = hash(metric, device_id)`，O(1) 定位；只有低基数标签（区域、型号、固件版本）进倒排索引，用 Roaring Bitmap 存 posting list。这是千万基数下索引能控制在几 GB 的关键。

### 2. 分片：按设备哈希分片，分片内按时间分区

- 1000 万设备 / 每分片 1 万设备 = 1000 个分片，20 个节点每节点 50 个分片
- 同一设备永远在同一分片，单设备查询只命中一个节点
- 分片内按天分区，分区目录只增不改，**TTL 删除 = 删目录**，O(1)
- 每个分片由一个线程独占（thread-per-core），MemTable 不需要锁；跨分片查询用 channel 发消息

初期可以先用 `crossbeam-skiplist` + 分片级 `RwLock` 简化，再演进到 thread-per-core。

### 3. 存储引擎：LSM + 列式文件

**写入链路**：WAL（group commit，每 5～10 ms 批量 fsync）→ MemTable（按 series_id 分桶，每个序列是预分配的列向量）→ 达到阈值后 flush 为不可变列式文件。

**文件布局**（每个分片每天一个或几个文件）：

```
[Chunk 序列A 0-1h][Chunk 序列A 1-2h]...[Chunk 序列B ...]...
[Footer: series_id → [chunk offset, len, min_ts, max_ts, count] 有序数组]
[Bloom filter on series_id]
```

数据按 `(series_id, ts)` 排序，一个设备一天的 8640 行在文件中是连续的一段（约 140 KB），一次 `pread` 取出。查 30 天 = 30 个并行读，NVMe 上 10～30 ms。

**编码**：时间戳 delta-of-delta + Simple8b/bit-packing；浮点 Gorilla XOR；整数 ZigZag + delta + bit-packing；字符串字典编码；块级再做 LZ4（热）或 Zstd（冷）。

**Compaction**：只在时间分区内部做，把多个小文件合并成大文件、消除重复和乱序；跨天的数据不互相干扰，写放大可控。已经关闭的分区可直接上传对象存储。

### 4. 乱序与回填

IoT 设备离线后会一次性补传几小时数据，这是常态而不是异常：

- 每个分区维持一个"开放窗口"（如 2 小时），窗口内乱序直接写 MemTable，flush 时排序
- 超出窗口的数据写入独立的 late 文件，compaction 时合并
- 查询时合并主文件和 late 文件，重复时间戳 last-write-wins

### 5. 查询路径：按类型分别保证毫秒

| 查询类型 | 路径 | 延迟来源 |
|---|---|---|
| 设备最新值 | Last-Value Cache（每序列一份最新行，1000 万 × ~100 B ≈ 1 GB） | 内存访问 |
| 单设备近 1 小时 | hash → 分片 → MemTable + 最近一个文件 | 1～2 次 IO |
| 单设备 30 天 | hash → 分片 → 30 个分区并行读连续 chunk | 30 次并行 IO |
| 单设备 30 天趋势图 | 读 1 分钟/1 小时降采样表 | 数据量减少 60～3600 倍 |
| 区域平均温度 | 读流式预聚合表（region × 1min） | 结果行数级别 |
| 按型号筛选设备 + 聚合 | 倒排索引 bitmap 求交 → 并行扫描 | 命中设备数决定，可能超毫秒 |

执行层用 Arrow 列式内存格式 + 向量化算子，谓词下推到 chunk 级（min/max 裁剪），只解码需要的列，延迟物化。

### 6. 预聚合：毫秒级跨设备聚合的唯一途径

写入时同步维护流式 rollup：

- 时间维度：1 分钟、1 小时降采样（min/max/avg/count/sum/last）
- 空间维度：按区域/型号/租户的分组聚合

查询优化器根据时间范围和请求的分辨率自动选择原始表还是 rollup 表。代价是写入 CPU 增加 20%～30%、存储增加约 10%，换来的是绝大多数仪表盘查询从秒级到毫秒级。

### 7. 冷热分层

| 层 | 数据范围 | 介质 | 查询延迟 |
|---|---|---|---|
| 热 | 最近几小时 | 内存 MemTable + 页缓存 | < 10 ms |
| 温 | 最近 7～30 天 | 本地 NVMe | 10～50 ms |
| 冷 | 更早 | S3/OSS + 本地块缓存 | 百毫秒到秒 |

计算节点可以做成无状态（数据在对象存储，本地只是缓存），扩缩容只需迁移分片归属，不需要搬数据。

### 8. 高可用

三种方案，复杂度递增：

1. **外部日志当 WAL**：IoT 平台通常已有 Kafka/Pulsar，数据库从 topic 消费，副本 = 多个消费者。最简单，HoraeDB 和 InfluxDB IOx 都走过这条路。
2. **分片级 Raft**：每个分片组 3 副本，`openraft` 实现。强一致但工程量大。
3. **共享存储 + 单写多读**：WAL 和数据都在对象存储，主节点故障后备节点接管回放。

## 六、Rust 实现要点

### 核心类型草图

```rust
type SeriesId = u64;   // hash(metric, device_id)，device_id 不进倒排
type Timestamp = i64;  // 毫秒

/// MemTable 中一个序列的列式缓冲，预分配避免热路径分配
struct SeriesBuffer {
    ts: Vec<Timestamp>,
    fields: Vec<ColumnBuffer>,     // 每个测点一列
    sorted: bool,                  // 乱序到达时置 false，flush 前排序
}

/// 不可变文件 footer 中的索引项，按 series_id 排序后二分查找
#[repr(C)]
struct ChunkMeta {
    series_id: SeriesId,
    offset: u64,
    len: u32,
    count: u32,
    min_ts: Timestamp,
    max_ts: Timestamp,
}

/// 分片由单线程独占，对外只暴露消息接口
enum ShardCommand {
    Write { batch: RecordBatch, ack: oneshot::Sender<Result<()>> },
    Query { plan: ScanPlan, tx: mpsc::Sender<RecordBatch> },
    Flush,
}
```

### 运行时与 IO

- **网络用 tokio，CPU 密集任务绝不放在 tokio worker 上**：解码、compaction、聚合放到独立线程池（rayon 或第二个 runtime），否则一次大 compaction 会让所有查询 p99 飙升
- **慎用 mmap**：在 async 上下文中缺页会阻塞整个 executor；优先显式 `pread`，追求极致时用 io_uring（`tokio-uring` / `monoio` / `glommio`）
- 用 `bytes::Bytes` 做零拷贝切片，chunk 从磁盘读出后直接切片传给解码器

### 内存与性能

- 换 `jemalloc` 或 `mimalloc`，并开启 profiling 查碎片
- 标签值 intern 成 `u32`，热路径不出现 `String`
- 解码循环写成固定步长的分块形式让 LLVM 自动向量化；需要时用 `std::simd` 或 `wide`，每个内核都配 `criterion` 基准
- `unsafe` 只允许出现在编解码内核，并且全部接入 `cargo-fuzz`

### 推荐 crate

| 用途 | crate |
|---|---|
| 列式内存与执行 | `arrow`, `parquet`, `datafusion` |
| 网络协议 | `tonic`, `arrow-flight`, `axum`, `rumqttc` |
| 压缩 | `zstd`, `lz4_flex`, `bitpacking`（Gorilla 建议自己写，几百行） |
| 索引 | `roaring`, `fst`（标签值字典） |
| 对象存储 | `object_store` 或 `opendal` |
| 缓存 | `foyer`（混合内存/磁盘缓存）, `moka` |
| 并发 | `crossbeam`, `parking_lot`, `crossbeam-skiplist` |
| 共识 | `openraft` |
| 测试 | `proptest`, `cargo-fuzz`, `criterion`, `turmoil`/`madsim`（确定性模拟） |
| 可观测 | `tracing`, `metrics`, `opentelemetry` |

## 七、怎么验证指标达成

1. **用 TSBS 的 iot 场景或自造负载生成器**，设备数、上报频率、乱序比例、离线回填比例都可配置
2. **查询延迟必须在写入满载时测**，空载的 p99 没有意义
3. 固定几类"黄金查询"写进 CI 基准，每个 PR 跑一遍，回归超过 10% 就失败
4. 故障测试：kill -9、磁盘满、时钟回拨、网络分区，验证恢复时间和数据不丢
5. 基数压测：从 100 万序列拉到 1 亿，观察索引内存和写入吞吐的曲线，找到拐点

## 八、要对外说清楚的现实边界

- **毫秒级是对特定查询类型在热/温数据上的 p99 承诺**，不是对任意查询的承诺，SLO 里要写明查询类型
- 冷数据首次查询、缓存冷启动后的第一波查询、正则匹配标签的高基数筛选，都做不到毫秒
- 预聚合是用写入 CPU 和存储换查询延迟，聚合维度需要提前规划，不能覆盖事后才想到的分析需求

总结成一句话：**千万设备靠"设备 ID 直接哈希、低基数标签才建倒排"控制索引规模；亿级记录靠列式压缩和时间分区控制存储；毫秒查询靠"按设备分片 + 设备数据物理连续 + 预聚合"让查询不碰无关数据。** 这套设计与 VictoriaMetrics、InfluxDB IOx 和 HoraeDB 新引擎 RFC 的思路是一脉相承的，区别主要在宽表模型和 IoT 特有的乱序回填处理上。
